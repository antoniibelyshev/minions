# QA sweep pilot, October 2026 (task-24)

A repo-wide coverage and performance sweep, run once on this repository to learn which signals produce
useful findings. The method below is meant to fold into the QA-sweep kind from task-22.

Measured on 2026-10-23 at base `facec2b`, Node 22.23.3, Backlog.md 1.54.0, vitest 4.1.12, a 16-core
Linux container shared with other running workers. Wall times on this host vary by up to 2x with
load from the other workers, so every timing below is a range over repeated runs; compare ratios and
scaling, not single numbers.

### P1: Backlog listing is 1+N process spawns

`BacklogMdAdapter.listTasks()` (`src/backlog/backlogmd.ts`) runs `backlog task list --json`, then one
`backlog task view <id> --json` per task at concurrency 4, because the list output has no description,
dependencies or acceptance criteria. Each `backlog` call is two processes (the node shim
`backlog.md/cli.js` and the compiled binary). Callers include `status`, `backlog list/export`,
`work next`, `work claim`, scheduler capacity, the Stop hook, `ci.ts`, intake sync and `addDependency`.

`npm run qa:perf` (throwaway state dir, see the recipe), median ms, two runs each:

| Command | 6 tasks | 40 tasks | 100 tasks |
|---|---|---|---|
| `node -e 0` (baseline) | 11 | 10-11 | 11-14 |
| `minions --version` | 48 | 49-53 | 49-52 |
| raw `backlog task view --json` (one task) | - | 47 | 56 |
| `minions backlog show` | 97 | 104-376 | 119-121 |
| `minions backlog ready` | 141 | 501-813 | 1594-1845 |
| `minions status` | 205 | 903-1500 | 3017-4919 |
| `minions backlog list` | 191 | 901-1736 | 3074-4982 |
| `minions work next` | 185 | 899-2190 | 3083-5731 |
| `minions work claim` | 410 | 1441-1937 | 4813-7191 |
| `minions work record` | 294 | 334-419 | 441-672 |

A single task view costs ~0.1 s end to end, so the cost is the per-task fan-out: roughly 30-50 ms per
task per listing on this host. The coordinator calls these several times per turn.

Fixed in task-24.1: listings parse the task files in-process and spawn one `task list` (falling back to
`task view` only for files outside the layout Backlog.md writes). `npm run qa:perf --tasks 100 --runs 5`,
median ms before/after on the same host: `status` 3071/137, `backlog list` 3389/134, `backlog ready`
1596/138, `work next` 3075/137, `work claim` 3509/461.

### P2: Repeated backlog reads in one invocation

- Stop hook (`src/runtime/hooks.ts:86-87`): `listReady(50)` then `listTasks()`; listReady views every
  ready task again.
- `work claim` (`scheduler.ts`): `getTask` per dependency, then `listTasks()`; its median is 1.5-2x a
  single `backlog list`.
- `addDependency` (`backlogmd.ts`): two `getTask` calls, then `listTasks()`.

One snapshot per invocation removes the multiplier even before P1 is fixed.

### P3: Bundle size and startup

esbuild metafile for `dist/cli.js`: zod 751 KB, `src/host` 412 KB, `src/runtime` 337 KB, commander
109 KB, everything else under 60 KB each. A minified build would be 1,115,886 B. `import { z } from 'zod'`
(zod 4 classic) pulls in the whole library, locales included. About 40 ms of every CLI call is module
evaluation. That is small next to P1 but paid on every hook run.

`npm test`: 105 files, 1668 tests (1 skipped). Wall time was 39.7-74 s across four runs on the shared

### Not done in the pilot

- Mutation testing (Stryker) was skipped. Each mutant needs at least the affected test files, the
  full suite takes 40-75 s, and a useful run over even one gate module would take well over the
  few-minute budget. task-24.6 suggests a scoped spike on merge/publish/hooks.
- No findings were fixed. The pilot only added the measurement tooling.

## Commands used

```bash
npm ci
npm run coverage                       # vitest run --coverage: text table + coverage/coverage-summary.json + coverage/index.html
npx vitest run --coverage --coverage.reporter=json --coverage.reportsDirectory=$TMPDIR/covjson   # per-function detail
npx vitest run --reporter=default --reporter=json --outputFile=$TMPDIR/vitest.json             # per-test durations
npm run qa:perf                        # build + scripts/qa-perf.mjs (defaults: 40 tasks, 5 runs)
node scripts/qa-perf.mjs --tasks 100 --runs 3
node -e 'import("esbuild").then(...metafile...)'   # bundle composition (see P3)
```

`scripts/qa-perf.mjs` creates a fresh `mkdtemp` root and points `MINIONS_STATE_DIR`, `MINIONS_CONFIG`,
`MINIONS_WORKSPACE`, `MINIONS_SECRETS_DIR`, `MINIONS_PLUGIN_DIR` and `MINIONS_SCRATCH_DIR` into it. It
writes a project-owner config and a Backlog.md config from the real source, seeds N tasks (half
ready, with dependencies), times each command after one warm-up, claims and records real leases, and
deletes the root at the end. It never touches `/state`.

## Recommended repeatable sweep recipe

Run as a QA-sweep task (task-22 kind) on the base branch.

| What | Command | Threshold, or what to flag | How often |
|---|---|---|---|
| Coverage | `npm run coverage` | total lines below 85% or branches below 75%; any security-gate module (hooks, scheduler, publish, merge, ci-gate, approval, credentials, upgrade, setup) below 90% lines or 75% branches; any module above 100 lines below 50% lines; a drop of more than 2 points against the previous sweep | monthly and after each large feature |
| Hot paths | `npm run qa:perf` and `node scripts/qa-perf.mjs --tasks 100 --runs 3` | `status`/`backlog list`/`work next` above 1 s at 100 tasks; `work claim` above 2 s; any command growing faster than linearly between 40 and 100 tasks | monthly, and before/after any backlog-adapter change |
| Startup and bundle | qa:perf header rows | `minions --version` more than 60 ms above `node -e 0`; `dist/cli.js` growth above 10% since the last sweep | monthly |
| Test-suite speed | vitest JSON reporter (above) | any single test above 3 s; suite wall time above 90 s on the reference host | monthly |
| Test strength (optional) | Stryker on one gate module, scoped to its test files | surviving mutants in decision branches | quarterly, only if the scoped run takes under 10 min |

File each finding as a backlog task with key `qa-sweep:<yyyy-mm>:<n>`, provenance `observed-result`,
parent the sweep task, status `idea`. Repeat the numbers in the sweep doc so the next sweep can compare.

### Lessons from the pilot

- Signals that produced useful findings: the per-module coverage table sorted by uncovered lines (not
  by percentage), and hot-path timings at two backlog sizes, which exposed the scaling problem in P1.
- Signals that were noisy: absolute wall times on a shared host, and percentages on tiny modules.
- Per-function coverage (the JSON reporter) is what turns a low number into a concrete test task.
