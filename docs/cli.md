# minions CLI reference

The README lists only the everyday commands. This page lists every command, grouped the same way
as `minions help --all`. The grouping is a help-text decision only: every command below works the
same whether or not the default `minions --help` lists it. The rationale is in
[design/cli-surface.md](design/cli-surface.md).

- `minions --help` (or `minions help`) lists the primary commands.
- `minions help --all` also lists the advanced and internal commands (`--json` returns the groups).
- `minions help <command> [<subcommand>]` (or `minions <command> --help`) shows the details of one command.

## Primary commands

These are the only commands most users need.

| Command | Purpose |
| - | - |
| `minions setup [path]` | Guided end-to-end setup: init wizard (including the runtime and Claude authorization), the guided GitHub flow (remote, base branch, token) and delivery mode, CI guidance, auto-merge (opt-in with pull-request delivery, default no), Telegram, which agent does the work (Claude Code by default; OpenAI Codex CLI asks for the OpenAI key and model and, in this version, adds the read-only `codex-reviewer` stage after the Claude reviewer in a workflow you pick; not asked in the host runtime or with `--yes`; see [Other agents](../README.md#other-agents-openai-codex)), the optional host manager bot (host-wide: its own bot token, then terminal pairing with a one-time code; see [host-manager.md](design/host-manager.md#token-isolation-for-the-manager-bot)), runtime start, import, coordinator launch, attach and pairing instructions, then an offer to open the setup assistant (`--yes`, `--dry-run`, `--delivery`, `--github-token-stdin`, `--telegram-token-stdin`, `--manager-token-stdin`, `--no-attach-coordinator`, `--no-assistant`; `--config`, `--attach`, `--new-identity`, `--runtime` as for `init`) |
| `minions setup github` | Guided GitHub setup: remote, base branch on the remote, pre-filled fine-grained token, delivery mode (`--yes` prints the next steps only; see [GitHub setup](../README.md#github-setup)) |
| `minions setup assist` | AI setup assistant: opens your host Claude Code with a minions setup skill to finish the remaining setup (interactive; `--dry-run` prints the command; see [Setup assistant](../README.md#setup-assistant)) |
| `minions start` | Build the image if needed, start the container, import the repo, attach the coordinator (`--no-attach`) |
| `minions status [--check]` | Queue, workers, pause state, config revision, delivery mode, channel (configured vs effective), pending notifications, spend (`spend` in `--json`: total, today, per task, coordinator, and the owner budget with `percent`; see `work spend`). Docker runtime: also whether the running container needs `minions upgrade` (`restartRequired` in `--json`: newer image, CLI version mismatch, credential mounts changed or missing, stale coordinator launch fingerprint). `--check` runs the host health checks instead (same as `minions doctor`) |
| `minions settings [--list] [--shared]` | Interactive settings menu (grouped, arrow keys; numbered prompts without a terminal): each item shows its value, source and effect. `--list` (with `--json`) lists every setting with `value`, `source`, `apply` (`live` / `prompt` / `launch` / `recreate`), `class` (`live` / `restart` / `recreate`), `hostOwned`, `needsRegenerate`, `needsRestart`, `needsUpgrade`, `canLoosen`; tokens only as provisioned/missing. Saves to the host-only `config.local.json` (`--shared`: the shared `.minions/config.json`, shared installs only). The Agents group has `harnesses.default`, the OpenAI key for Codex (`secrets.codex`) and one `roles.<role>.harness` item per worker role (a process harness only where this version allows the role). See [Changing settings](../README.md#changing-settings) |
| `minions settings set <key> <value>` | Change one setting: schema-validated before writing; loosening changes need a confirmation or `--yes`; regenerates the runtime config and plugin; restart-needing changes offer a graceful coordinator restart (`--restart`, `--no-restart`, `--shared`, `--dry-run`). The output says when the change takes effect (`--json`: `takesEffect` `now` / `restart` / `upgrade`, with `class` and `hostOwned`); `upgrade` changes print `minions upgrade` as the next step. `pause.intake` / `pause.starts` (`paused` / `running`) run `minions pause` / `resume` in the runtime. `--expect-revision <n>`: refused (`CONFLICT`, nothing written) unless the config is still at configRevision `n` (a local-layer write does not bump the revision; the shared file's edits do). **In the agent runtime** it records a change request instead (`--reason <text>` required; validated against the runtime config; host-owned keys refused with `CONFLICT`); nothing is applied until the owner runs `settings apply` on the host |
| `minions settings requests [--all]` | Change requests recorded in the runtime (`settings set`, `settings restart`, `upgrade` run there): id, kind, payload, reason, status (`proposed` / `confirmed` / `applied` / `failed` / `rejected` / `expired`; a newer request for the same thing expires the older one). Open ones by default (proposed, confirmed, failed). On the host it reads them through the runtime |
| `minions settings apply <id> [--yes] [--confirm <digest>] [--dry-run]` | Host only: re-validate a change request against the host config and show the host-computed plan (diff, layer and file, class, what it loosens, what it interrupts, the commands it runs) with its sha256 digest; the reason is shown quoted and cut to 300 characters. Confirm in the terminal (loosening plans ask twice) or with `--yes`; without a terminal the plan is offered (journaled in `<MINIONS_HOME>/manager/journal.jsonl` with a single-use nonce) and applied later only by `--confirm <digest>` within 30 minutes, if the plan and configRevision are unchanged. Applies through `settings set --expect-revision` (no restart: a needed restart is a next step), the graceful `settings restart`, or `minions upgrade`, then marks the request `applied` / `failed` |
| `minions settings reject <id> [--reason <text>]` | Host only: mark an open change request `rejected` (nothing is applied) |
| `minions settings restart` | Graceful coordinator restart (`coordinator restart --recover` in the runtime; refused while worker leases are active; `--dry-run` restarts nothing). In the agent runtime it records a restart request (`--reason <text>`) |
| `minions upgrade [--timeout <s>] [--now] [--from-container [branch]] [--rebuild-cli] [--sync-only] [--dry-run]` | Move the running container onto the installed minions: pause starts and request a drain (active workers commit work in progress as `wip:` and return partial results; recovery re-dispatches them), wait for the workers (or release them with `--now`, reported as interrupted), rebuild the image only if the package changed, recreate the container with volumes kept, restart the coordinator with recovery, resume starts. With `--from-container` (`local` delivery only), first export the container branches and fast-forward `branch` (default: the base branch) to `minions/<base>`; this happens only on a strict fast-forward with clean working trees, and the command never merges, resets or force-updates. When the project is a minions checkout and the installed CLI differs from it, the upgrade stops and prints the rebuild command; with `--rebuild-cli` (you reviewed the checkout: this runs its npm scripts and build on the host) the CLI is rebuilt (linked install) or reinstalled (`install.sh` install; the replaced install is first kept as a tarball in `<MINIONS_HOME>/manager/cli-backup/`, the last 2, for the host manager's Roll back CLI) and the rest runs on the new CLI. Commits just taken with `--from-container` are never built in the same run. With `branch` / `pull-request` delivery the CLI comes only from the reviewed `origin/<base>` commit: the upgrade fetches origin, fast-forwards the base, and refuses `--from-container` (see [Delivery, review, and merging](../README.md#delivery-review-and-merging)). For other installs, such as git-URL ones, it prints the exact command and stops before touching the container. Docker runtime only: in the host runtime it refuses and points to `minions down && minions start`. With `--sync-only` only the source sync runs (the host manager's `/sync`): `local` delivery exports the container branches and fast-forwards the base branch, GitHub delivery fetches `origin/<base>` and fast-forwards; no CLI or container step, and the same strict rules (a dirty tree or a divergence refuses). In the agent runtime it records an upgrade request (`--from-container [branch]` and `--reason <text>` only) for `settings apply` on the host |
| `minions down` (alias `stop`) | Stop and remove the project container (volumes kept), or stop the host runtime's tmux server |
| `minions uninstall` | Remove owned files while keeping task data (`--delete-data` also deletes volumes) |

## Advanced commands

Single setup steps and fine-grained control. `minions setup` runs `init`, `auth github`,
`auth telegram`, `start` and `import` for you, and rerunning `minions setup` changes any of
those choices. `minions doctor` is the same check as `minions status --check`.

| Command | Purpose |
| - | - |
| `minions init [path]` | Inspect and initialize a project (`--private` / `--shared`, `--runtime docker\|host`, `--yes`, `--dry-run`) |
| `minions doctor` | Check tools, Docker (or the host runtime's tmux/claude/backlog/git), image, container, Claude auth, backlog CLI, deferred features, and the `restart` check (same restart-required reasons as `minions status`; a warning naming `minions upgrade`, never a failure; `restartRequired` in `--json`) |
| `minions auth show` / `set <login\|api-key\|helper\|jbcentral>` / `refresh` | Host-side Claude authorization (see [Claude authorization](../README.md#claude-authorization)) |
| `minions auth github` / `telegram` | Store (or `--remove`) the project's GitHub token / Telegram bot token on the host; prompted without echo or `--stdin` (`telegram` offers to switch a `terminal` channel to `auto`) |
| `minions auth codex` | Store (or `--remove`) the OpenAI API key for Codex process workers on the host; prompted without echo or `--stdin`. Only the process runner reads it (as `CODEX_API_KEY`, never in argv); `minions setup` asks for it when you choose Codex |
| `minions config show [--explain]` / `config list` / `config set <key> <value>` | Alias of `minions settings`: the raw effective config with provenance, the settings list, one setting change |
| `minions config roles list [--all]` / `show <name\|proposalId>` | Read-only (host and runtime): the worker roles (built-ins and project roles, with the workflows using each) and the role proposals (pending; `--all`: also applied and superseded). `show` prints one role (fields, tools, policy column) or one proposal with its summary. On the host, proposals are read from the running runtime. See [Custom roles](../README.md#custom-roles) |
| `minions config roles apply <proposalId>` | Host only (rejected inside the runtime): read the proposal from the runtime, validate it against the host config, show the config diff and the prompt (control characters stripped, the prompt fenced; a `LOOSENS:` line lists capabilities the role gets looser than the profile), confirm (`--yes`; `--dry-run` shows the diff only), write `roles.<name>` (with `prompt: agents/<name>.md`) and the proposed `workflows` plus the prompt file next to the project config (`configRevision` + 1, runtime config and plugin regenerated) and mark the proposal applied. Never commits (shared installs: a reminder to commit `.minions/`) and never restarts: restart required (`minions settings restart`) |
| `minions config roles remove <name>` | Host only: remove a project role from the project config (`--yes`, `--dry-run`; `configRevision` + 1; restart required). Refused for built-in roles, while a configured workflow (or another role's `repairTo`) uses the role, while an active lease has that role, and when the runtime is not running (the leases cannot be checked). The prompt file is left in place |
| `minions channel show` / `set <auto\|terminal\|telegram>` | Configured vs effective communication channel; set it in the project config (`configRevision` bump, `--yes`, `--dry-run`; restart-required; see [Communication](../README.md#communication)) |
| `minions runtime show` / `set <docker\|host>` | Host-side agent runtime: Docker (default) or the less safe host runtime (`--global`, `--yes`, `--dry-run`; see [Running without Docker](../README.md#running-without-docker)) |
| `minions import` | Refresh the container workspace from the committed base branch (Git bundle) |
| `minions import --state <file> [--force]` | Restore a state backup written by `export --state` into the running runtime: validated on the host and in the runtime (manifest format and version, per-file sha256, allowed paths, regular files only, DB integrity and schema) before anything changes; refused (`CONFLICT`) while a worker lease is active or a live coordinator holds the project lock unless `--force`; leases the backup has active are released and a live coordinator keeps its lock row, so `minions settings restart` (recovery restart, re-dispatches the released tasks) works afterwards; the replaced state is moved to `<state>/pre-restore/<time>/` (newest three kept). `--dry-run` only validates the archive. See [troubleshooting.md](troubleshooting.md#before-risky-steps-back-up-the-runtime-state) |
| `minions export` | Fetch the container clone's branches (`agent/*`, and the integrated base as `minions/<base>`) into `refs/remotes/minions/*` in your repository; local branches are untouched |
| `minions export --state [file]` | Back up the runtime state instead: backlog, notes, worker briefs and results, the coordinator handoff and a consistent runtime DB snapshot (`VACUUM INTO`) in a gzip'd tarball with `manifest.json` (format version, creation time, schema version, size and sha256 per file), mode 0600, default `<project>/exports/state-<time>.tar.gz`, never overwritten. Never includes secrets, tokens or the Claude login; `import/`, `exports/`, `logs/`, caches and the workspace are excluded; symlinks, hard links, secret-like names and files containing a mounted token are skipped and listed in the manifest. Needs the runtime running |
| `minions pause` / `resume` | Persist scheduling controls. `--intake` / `--starts` select one (default: both). `pause --drain [--reason <text>]` also pauses starts and asks leased workers to wind down (commit `wip:`, return partial); `status` shows `draining`; `resume --starts` (or `resume --drain` alone) clears it. Paused starts stop new task starts; paused intake makes `minions backlog create` refuse new work from requests or tickets (`POLICY_DENIED`), while creation from existing work stays allowed: a `--parent`, a `split:` / `followup:` / `qa:` idempotency key, or provenance `observed-result` (keys starting with `intake:` are always refused) |

## Internal commands

Used by the coordinator, the workers, the Claude Code hooks and the container. You normally don't
run these yourself. They are not listed by the default help.

| Command | Purpose |
| - | - |
| `minions work next` | Read-only: the stages that can be claimed now, in dispatch order (tasks under way first, then priority), with capacity, per-role limits, pauses, drain and the budget applied. `runnable` entries are `{taskId, role, agentType, position, workflow, suggestedModel, agentModel, reason}`; `waiting` adds `waitingOn` (`starts`, `capacity`, `role-capacity`, `harness-capacity`, `requires`); every entry also has `harness` and `launch`: `{kind: "agent", agentType, agentModel}` for Claude Code, or `{kind: "run", command: "minions work run <leaseId> --json", harness, model, effort, deep}` for a role on a process harness (claim, then run the command in the background, then record); `stuck` lists tasks in a stage status without a lease that no stage can be claimed from. `suggestedModel`: stage `model` hint > role `model` > risk rule (`risk:high` or a repair after a failed attempt: the strongest allowed alias and the `-deep` variant; `risk:low` or an all-hinted workflow: the cheapest allowed alias for gate and verifier stages) > `models.default`; with `models.selection: "fixed"` always the default. `agentModel` is the Agent call's `model` (null = omit) |
| `minions work claim <taskId> [--role <role>]` / `record` / `release` / `list` | Leases and worker results (used by the coordinator, inside the container). `claim` takes the task's current stage; `--role` is optional and refused unless it names that stage's role. `record` / `release` take `--usage <tokens> [--model <name>]`: the worker's token total from the task notification, stored per attempt (the latest figure per lease counts, so a correction never double-counts); the response carries `budget` (with `crossed` 50/80/100 to report) |
| `minions work cancel <taskId...>` / `--all` `[--reason <text>]` | Best-effort cancel: release every active worker lease of those tasks (or all) without a result; worktrees and branches are kept, a late worker submit is refused. Works from the host terminal (delegated to the runtime). The owner's "cancel <task>" control |
| `minions notify enqueue --key <key> --kind <kind> [--task <id>]` / `pending [--all]` / `ack <key...> [--via <transport>]` / `fail <key> --error <msg>` | Durable notification outbox: the coordinator records each owner notification (text on stdin) under a dedup key before sending it, then acks it; a failed send stays pending and is retried after a backoff on the next interaction or `sync`. A key is delivered once. `status` and `sync` show the pending count. See [design/telegram.md](design/telegram.md#notification-outbox) |
| `minions work spend [--budget <amount> [--by <name>]] [--lease <leaseId> \| --session [id]] [--tokens <n>] [--model <name>]` | Spend tally and the owner budget. `--budget` takes plain language: `"5M tokens"`, `"500k tokens per day"`, `"20 attempts"`, `"$50"` (API-key billing only; estimated), `off`. At 100% new claims are refused (`POLICY_DENIED`, "Budget reached"); running workers are never stopped. `--lease`/`--session` with `--tokens` record a worker's or the coordinator session's own cumulative total after the fact. The coordinator's own tokens are measured from its transcript by the Stop hook (per Claude session id); `--session --tokens` overrides that session's measured figure (default id: the current Claude session), it is never added to it. `--json` has `coordinator.baseline` (sessions and resets by trigger, turns, context per turn, tokens per delivered task and per owner message, reset overhead, coordinator share; weighted USD with API-key billing); the human output shows it in three lines, `minions status` only the coordinator total. Tokens are authoritative; USD (API-key billing) is a rough estimate because notification totals do not separate cache tokens (the Console usage page is authoritative). On a Claude subscription only tokens and attempts are counted: the remaining plan quota is not visible to minions |
| `minions work brief <leaseId> --role <role>` | Worker: fetch the full brief of your own lease (run from inside its worktree) |
| `minions work submit <leaseId> --role <role> [--result-file <path>]` | Worker: submit your WorkerResult JSON (stdin or file) for the coordinator to record |
| `minions work probe [--refresh]` | Process-harness probe, inside the container, with no credentials and no model request: each configured process harness binary and its pinned version, the `minions-sandbox` isolation self-test (canaries for every Landlock, seccomp, descriptor and process-lifetime restriction; run once per container start and cached in `/state/run/sandbox-probe.json`, `--refresh` reruns it), and loopback listeners on allowed TCP connect ports. `status --check` / `doctor` report it as `harness.<id>` and `harness.network` when a process harness is configured |
| `minions work run <leaseId>` | Coordinator (Bash, in the background), for a lease whose role runs on a process harness. Runs the launch gate (active lease, phase rules, one run per lease, no unfinished run of the same task, drain/pause/budget, capacity counting the other leases, the isolation self-test). Then it writes the run record in `/state/run/leases/<id>/`, passes the brief by proxy, makes a private per-lease clone and runs the worker under `minions-sandbox` with supervision (wall clock, cancel, drain). After the worker exits it runs the post-exit checks, does a fast-forward-only fetch-back and submits the result by proxy. Prints one JSON line (`leaseId`, `exit`, `submitted`, `status`, `violations`, `usage`, `wipCommit`, `head`) when the worker ends; then run `work record --submitted` without `--usage` (the runner recorded the usage). The Codex adapter ships for gate roles (phase 1 option b, the `codex-reviewer` pilot); the runtime image ships the pinned `codex` CLI (`MINIONS_CODEX_VERSION`). Junie has no adapter yet (`PRECONDITION`) |
| `minions work publish <taskId>` | Publish (or retry publishing) an approved task in branch / pull-request delivery; idempotent. With `delivery.merge: "auto-when-eligible"`, also runs the auto-merge pass for the delivered PR |
| `minions work approve <taskId> --head <sha> [--merge]` | Record your approval (signed on the host) to publish that exact commit (sensitive paths, or `ask` publication); with `--merge`, to merge its delivered PR (`pr.merge` `ask`, CI-gated auto-merge) |
| `minions config roles propose --file <f>` | Coordinator (runtime only): validate a role proposal `{name, role, promptText, reason, workflows?}` with the config rules (schema, role-name rules, workflow invariants, prompt checks) and store it in the runtime DB (`role_proposals`) as `pending`; a newer proposal for the same name supersedes the pending one. Returns `proposalId`, a `summary` (fields, tools, edit scope, policy row, `loosens`: capabilities looser than the active profile) and `applyCommand`. Text with terminal control characters is rejected (newline and tab allowed in `promptText` only). Nothing becomes effective until the owner runs `config roles apply` on the host |
| `minions backlog ready` / `list` / `show` / `create` / `update` / `note` / `export` | Backend-neutral task operations (inside the container). `create` / `update --workflow <name>` assigns a named workflow from config `workflows` (stored in the task meta block; `update` only between stages) |
| `minions sync [taskIds...]` | Import issues matching `intake.github` into the backlog when enabled (also at coordinator start; skipped with a count while intake is paused; issues that leave the filter or are reassigned pause their task), then refresh PR state and CI check results for tasks with a PR and reconcile merged/closed PRs (merged → `done`). With `delivery.merge: "auto-when-eligible"` it then arms GitHub auto-merge for PRs that pass every gate for the approved head and disarms what it armed when a gate stops passing; otherwise read-only on GitHub. With task ids, only those PRs are refreshed |
| `minions ci status` | Required status checks on the base branch and the external CI setup plan (read-only) |
| `minions hook stop` / `pre-agent` / `pre-telegram` | Claude Code hook handlers (container only) |
| `minions coordinator` / `coordinator run` / `sync` / `restart` | Attach or launch the coordinator session; restart it (`minions start` attaches for you) |
| `minions coordinator restart [--recover] [--force] [--detach]` | Kill the coordinator session and relaunch it detached; refused while worker leases are active unless `--force`. `--detach` (the coordinator restarting itself for a context reset): check the leases and refuse during a drain unless `--force` (plain `restart` does not check the drain: the host upgrade uses it), run the restart in a detached process (output in `<state>/logs/context-reset.log`) and return at once, because the restart ends the calling session |
| `minions coordinator handoff` / `--read` / `--check` | Context-reset handoff (used by the coordinator itself). Text on stdin: store it at `<state>/coordinator-handoff.json`, redacted, at most 4 KB (refused above the cap; the previous one is kept), replacing the previous one. `--read`: print the stored handoff (a fresh coordinator reads it at startup). `--check`: whether a context reset is due (triggers, blockers such as active leases or a drain, the steps). Settings: `coordinator.contextReset` (on by default; `enabled: false` opts out). See [design/bootstrap.md](design/bootstrap.md#coordinator-context-resets) |
| `minions manager run` | Host only: the host manager loop in the foreground (one per host, `<MINIONS_HOME>/manager/lock`). Every 20 s it reads each running project's change requests (`settings requests --json` in the runtime; 30 s timeout, 256 KiB cap), offers each open one with the host-computed plan, and applies a confirmed offer by running the stored plan's host command as a child process. Until the manager bot is paired, offers and outcomes are JSON lines on stdout, and an offer is confirmed with the printed `minions settings apply <id> --confirm <digest>`. A restart refused because workers are active is followed by two plans to confirm: **Restart when idle** (queued in the manager, run at the first poll without active leases) and **Drain now** (`pause --starts --drain`, then the same restart once idle). After an upgrade that rebuilt or reinstalled the CLI it checks `minions --version` and `minions status`, and offers **Roll back CLI** (the newest backup) when that fails. The dev-only `/rebuild_cli` (`minions upgrade --rebuild-cli` with the commit range, diffstat and sensitive paths in the plan; always two taps) exists only when the host CLI runs from a minions source checkout and the project is minions. Normally started by its service. See [design/host-manager.md](design/host-manager.md) |
| `minions telegram probe` / `install` / `status` | Telegram channel plugin support (see [design/telegram.md](design/telegram.md)) |
| `minions workspace setup` / `import` / `export` / `state-export` / `state-import` | Container workspace and state setup, and the runtime side of `export --state` / `import --state` (container only) |

## Conventions

Planned, **deferred in v0.1**: `minions config plan` / `apply`, `minions review publish`, `minions merge request`, `minions migrate backlog`, and the plan/migration parts of `minions upgrade`.

Every command supports `--json`, and mutating commands support `--dry-run`. Exit code 0 means the requested operation completed (`doctor` and `status --check` exit non-zero when a check reports a blocking FAIL; warnings keep exit 0; `help <command> --json` prints the command's usage, subcommands and options); it does not mean a whole task passed. Errors use stable codes for auth required, conflict, policy denied, invalid configuration, incompatible runtime, and retryable network failure. Secrets and large task text go through stdin or restricted temporary files, never through process arguments.
